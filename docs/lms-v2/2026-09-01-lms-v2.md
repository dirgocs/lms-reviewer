# LMS v2 — contrato de revisão, qualidade do veredito e fix mode

**Data:** 2026-09-01
**Origem:** auditoria de segurança de 2026-08-31 (`docs/security-audit/`) + análise
comparativa entre o prompt de auditoria do Master, o `/code-review ultra` da Anthropic
e o LMS atual.

Este documento é o **porquê**. Os planos de execução são:

| Plano | Fase | Depende de |
| --- | --- | --- |
| `docs/superpowers/plans/2026-09-01-lms-v2-contrato.md` | 1 — contrato do scorecard | — |
| `docs/superpowers/plans/2026-09-01-lms-v2-veredito.md` | 2 — qualidade do veredito | Fase 1 |
| `docs/superpowers/plans/2026-09-01-lms-v2-fix-mode.md` | 3 — fix mode | Fase 1 |

Fases 2 e 3 são independentes entre si e podem rodar em lanes paralelas depois da 1.

## 1. O problema

O LMS já resolveu, um a um, os furos que importam num gate de revisão: reprovação
deixou de ser lida como falha do reviewer, o autor saiu da cadeia, a prova de leitura
é conferida contra o disco, o scorecard vale só para o `subject` que foi revisado, o
fallow não pode mais ser declarado `skipped`, e todo aceite passa por contraditório
com prova executável em allowlist.

O que sobrou é de outra natureza. Não são furos de mecanismo — são **lacunas de
informação**:

1. **Não existe denominador.** Um revisor que abriu 3 de 45 rotas e um que abriu as
   45 produzem scorecards indistinguíveis. `inspected` prova que ele leu *alguma
   coisa*, não que varreu a superfície.
2. **Lente vazia é ambígua.** `code-efficiency: {p0:0,p1:0,p2:0}` significa "limpo"
   ou "não olhei"? O gate não sabe.
3. **O único filtro de falso-positivo é auto-declarado.** `confidence >= 80` é o
   revisor dando nota à própria certeza — o mesmo conflito de interesse que o
   contraditório eliminou do lado do aceite, intacto do lado do achado.
4. **Não há memória de falso-positivo.** A mesma classe de achado ruim é
   re-litigada a cada rodada, e o custo é pago inteiro toda vez.
5. **Achado não tem identidade entre iterações.** O scorecard é um retrato. Não dá
   para dizer se o P1 da rodada 3 é o mesmo da rodada 2, nem se "corrigi" mudou
   código.
6. **Severidade é plana.** Não há onde registrar "só explorável com a flag X
   ligada", então achado teórico e achado vivo competem na mesma escala.
7. **O effort é fixo.** O grafo já diz que o diff toca `auth`/`tenant`/`fiscal` — e
   esse sinal só é usado para **limitar o score**, nunca para aprofundar a revisão.
8. **A cadeia inteira roda em diff de documentação.** Três providers acordados para
   julgar um `.md`, com cota semanal Claude compartilhada entre lanes.
9. **Formato inválido queima um provider.** JSON malformado é classificado como "não
   fez o trabalho" e cai para o próximo, quando o correto seria devolver o erro de
   validação e deixar tentar de novo.
10. **A correção volta para o orquestrador.** Quem achou o defeito tem o contexto
    exatamente do tamanho do defeito; o orquestrador precisa re-derivar tudo a
    partir de um resumo em prosa.

E um bug de conteúdo, achado durante a auditoria:

11. **O LMS manda procurar `hotel_id`.** `SKILL.md:417` e
    `scripts/local-merge-score-orient.mjs:56` (e também `.greptile/rules.md:12-13` e
    `apps/erp-web/AGENTS.md:16`) descrevem o isolamento multi-tenant por `hotel_id`.
    Essa coluna aparece em **zero** arquivos de código. A chave real é
    `tenantId` / `tenant_id`, que o `scripts/db-exposure-gate.mjs` usa corretamente.
    Todo revisor que seguir a regra ao pé da letra procura a coisa errada.

## 2. De onde vem cada solução

### 2.1 Do prompt de auditoria do Master

| Mecanismo | Vira o quê no LMS |
| --- | --- |
| "detecte a stack e mapeie cada categoria para o equivalente dela" | Instrução no `reviewPrompt`: identificar o mecanismo de isolamento **antes** de procurar onde ele falta. Foi o que fez a auditoria achar que o backend fiscal conecta como dono do banco e não passa por RLS. |
| "registre também o que foi verificado e está CORRETO" | Campo `verified` — asserções positivas com citação conferida no disco. **Afirmação positiva é barata de refutar**: basta um contraexemplo. Provar ausência de bug é caro; derrubar "está tudo escopado" é achar uma rota. Dá ao contraditório algo atacável. |
| "percorra TODOS os handlers, não amostras" | Campo `coverage` — `{surface, total, inspected}`. O denominador que falta. |
| "quando a categoria não se aplicar, diga isso" | `lenses.<lente>.applicable: false` + motivo. Desambigua lente vazia. |
| "note condições de explorabilidade" | Campo `precondition` no achado. |
| Critérios de aceite verificáveis por achado | Campo `acceptance` — o que transforma P2 adiado em algo que a próxima rodada confere. |

### 2.2 Do `/code-review ultra`

| Mecanismo | Vira o quê no LMS |
| --- | --- |
| Duas etapas: gerar → verificar adversarialmente cada achado, em paralelo | Novo estágio de verificação por achado. O contraditório de hoje ataca o **scorecard** (falso-negativo); este ataca **cada achado** (falso-positivo). Eixos diferentes. |
| `verdict: CONFIRMED \| PLAUSIBLE` separado de `confidence` | `confidence` é auto-avaliação e é gamificável — a história do codex aprovando em 17 s com 152 reasoning tokens está no próprio SKILL.md. `verdict` é resultado de outro provider. |
| HARD EXCLUSIONS + PRECEDENTS | `references/precedentes.md`, injetado no prompt e **crescendo uma linha a cada refutação vencedora**. |
| `outcome: fixed \| skipped \| no_change_needed` | Identidade estável de achado + desfecho por iteração. |
| Níveis de effort (`low`…`ultra`) | Effort derivado do raio de impacto que o graphify já calcula. |
| Triagem barata (Haiku) antes de acordar os revisores | Triagem **determinística** por caminho — mais barata e mais previsível que um modelo. |
| `ReportFindings` como tool tipada | JSON Schema publicado + retentativa com a mensagem de validação específica. |
| `--fix` | Fase 3. |

## 3. Decisões de desenho

### 3.1 O verificador por achado só rebaixa, nunca apaga

Um verificador que pode **deletar** um achado é um caminho novo para enfraquecer o
gate — vira "shopping por um verificador que descarta". Portanto:

- `CONFIRMED` → o achado bloqueia, como hoje.
- `PLAUSIBLE` → o achado **não bloqueia** a publicação, mas permanece no scorecard e
  vai para o backlog. É rebaixamento, não remoção.
- `FALSE_POSITIVE` → só é aceito com `proof: {command, expect}` que **rode e
  confirme**, usando a mesma allowlist `PROVAS_PERMITIDAS` que o contraditório já
  usa. Sem prova, cai para `PLAUSIBLE`.

O verificador nunca é o mesmo provider que achou, nem o autor.

### 3.2 O `--fix` é seguro porque o `subject` hash já existe

O invariante do LMS é **quem julga ≠ quem produziu**. Corrigir é produzir; pontuar é
julgar. O invariante só quebra se o revisor pontuar o delta que ele mesmo escreveu.

`scripts/lms-subject.mjs:47-52` mete no hash o `diff base...HEAD`, o `diff HEAD`
(árvore suja) **e** os arquivos não rastreados. Logo, um revisor que corrige muda o
subject, o scorecard morre na hora e `scorecardError` recusa
(`lms-scorecard.mjs:156-163`). **Aprovar o próprio conserto é estruturalmente
impossível.** A trava foi construída para outro problema (5/5 autorizando commit
posterior) e cobre este de graça.

O que ainda falta é fino: hoje `authorProvider` exclui o **provider inteiro** da
cadeia. Com fix de revisor, isso queima um revisor a cada correção. Precisa virar
exclusão **por arquivo**: R não pontua os arquivos que R tocou, mas pontua o resto.

### 3.3 Quem corrige sai da forma do achado

Se `fix` é um diff, o revisor corrige. Se é uma decisão, escala. Operacionalizado
com sinal que o sistema já produz:

| Sinal | Quem corrige |
| --- | --- |
| Fix cabe nos arquivos citados em `path` | revisor |
| Fix precisa criar/apagar arquivo, ou tocar arquivo fora dos achados | orquestrador |
| graphify indica raio alto / cruza comunidade | orquestrador |
| P2 mecânico repetido em N lugares | revisor, em lote |

### 3.4 O fix nunca escreve no próprio gate

Um agente com mandato de corrigir e incentivo de passar no gate, com acesso de
escrita ao gate, edita o gate. Denylist obrigatória, conferida **antes e depois**:
`.lms/`, `.claude/hooks/`, `scripts/lms-*`, `scripts/db-exposure-gate*`, `.git/`.

Mesma razão pela qual `PROVAS_PERMITIDAS` é uma allowlist fechada: o comando vem da
saída de um modelo.

### 3.5 Pontuar e corrigir são duas invocações

Nunca `score+fix` no mesmo turno — aí o revisor teria incentivo a achar o que ele
gosta de consertar. Pontuar continua read-only (`codex exec -s read-only`). Corrigir
é uma segunda invocação, com escrita limitada ao workspace, disparada só depois que
o orquestrador aprovou a lista.

## 4. Fora de escopo

- Gerador de relatório em PDF dentro do LMS. Gate de push não precisa de relatório;
  a auditoria de segurança já tem o dela em `docs/security-audit/`.
- Substituir as quatro lentes pelas cinco categorias do prompt de auditoria. As
  categorias são mais estreitas — entram como **checklist dentro de `code-safety`**,
  não como estrutura.
- Mexer no `greploop` ou em qualquer caminho que gaste crédito Greptile.
- Reescrever migrations existentes (`REGRA_MIGRATION_APLICADA` continua valendo).

## 5. Compatibilidade

`.lms/last.json` é estado de runtime, gitignored, e é **regenerado sempre que o
subject muda** — ou seja, a cada push com código novo. Não existe scorecard de longa
vida para migrar. Campos novos podem ser exigidos direto, sem período de tolerância:
o pior caso é uma rodada de revisão a mais no primeiro push depois do deploy.
