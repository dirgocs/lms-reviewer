**Data:** 2026-09-03
**Depende de:** Fases 1–3 (v1.2.0, `CHANGELOG.md`), spec base `docs/lms-v2/2026-09-01-lms-v2.md`
**Decidido por:** Master/Fable. Este documento é execução, não deliberação.

## 1. Contexto e motivação

As Fases 1–3 entregaram contrato (`coverage`, `verified`, `id`, `acceptance`),
qualidade do veredito (triagem, effort, precedentes, verificador por achado) e fix mode
(`lms-fix`, roteamento, guarda de escopo, autoria por arquivo). O que ficou de fora é o
**custo do laço**: hoje, corrigir um achado invalida o `subject`
(`scripts/lms-subject.mjs`, hash inclui árvore suja) e obriga uma **rodada cheia** de
15–30 min por achado corrigido.

Evidência:

1. **KDT-68 gastou 8 rodadas.** Cada uma acordou a cadeia inteira para reconferir
   achados que o próprio revisor tinha aberto e cujo `acceptance` já estava escrito.
   Re-verificar um fix custa 2–5 min; refazer a varredura custa 15–30.
2. **Cinco dessas rodadas foram da MESMA classe** ("paridade preview×emissão"), até
   nascer o teste de paridade. O gate estava premiando fix pontual: o revisor abria o
   próximo exemplo da mesma família a cada rodada, e ninguém tinha mandato para exigir
   o teste que fecha a classe. É a doutrina "fix the principle, not the example"
   ausente do mecanismo.
3. **Não há eval do próprio LMS.** Os relatórios de fechamento
   (`docs/lms-v2/2026-09-01-fase2-relatorio.md`, `…-fase3-relatorio.md`,
   `…-fix-review-fase3-relatorio.md`) mostram trocas de prompt e um provider novo
   (`pi`, v1.1.5) aprovados por leitura, sem medida de recall nem de falso-positivo.
   O corpus existe — `.lms/history.jsonl`, `.lms/reports/REVIEW-FASE{1,2,3}-OPUS.md` do
   consumidor — e nunca foi transformado em régua.
4. **Rodada gasta cota antes de saber se a árvore compila.** A triagem
   (`scripts/lms-triage.mjs`, exit 10) só pergunta *se o diff merece revisão*, nunca
   *se o diff está de pé*. Suíte vermelha consome três providers para produzir achados
   que o `node --test` daria de graça.

## 2. Escopo

Quatro itens, nesta ordem de dependência: 4 → 1 → 2 → 3 (o item 4 é o mais barato e
protege os outros; o 2 depende do histórico por rodada que o 1 passa a persistir).

## 3. Desenho

### 3.1 Re-verificação incremental do fix

Depois de `lms-fix` (ou de um fix manual), o runner devolve ao **mesmo revisor que
abriu o achado** (`finding.found_by`, carimbado por
`lms-reviewer-fallback.mjs:applyRefutation`, já usado em `lms-fix.mjs:runFix`) uma
pergunta estreita: *estes ids continuam abertos?*

**Contrato de entrada** (prompt novo, `lms-reverificar.mjs:reverificarPrompt`):

```
ids: [{ id, title, severity, path, acceptance }]
diff do fix: git diff <marco>..árvore, limitado aos arquivos das linhas do fix
```

**Contrato de saída** (um objeto por rodada, gravado em `.lms/reverificacao.json`):

```json
{ "reviewer": "grok",
  "results": [{ "id": "…", "status": "closed|open", "why": "…", "evidence": "…" }] }
```

Regras, todas fail-closed:

- `status: closed` **só remove o achado da lista bloqueante**. Nunca mexe em `score`,
  `aggregate` nem `coverage` — o scorecard reaproveitado mantém a nota da rodada cheia.
- Id que não aparece na resposta, ou id desconhecido, continua `open` (mesma defesa
  sem porta de saída que o P3-2 da Fase 3 instalou no verificador).
- Todo `closed` passa pelo **verificador independente da Fase 2**
  (`scripts/lms-verificar-achado.mjs`), que só rebaixa: verificador diz que o achado
  segue vivo → volta a `open`. `LMS_VERIFY=0` desliga o verificador e, com ele,
  **desliga a re-verificação inteira** (fechar sem contraditório é o buraco).
- Rodada cheia continua **obrigatória** quando: (a) a guarda de escopo da Fase 3
  registrou arquivos fora dos arquivos dos achados
  (`lms-fix-escopo.mjs:escopoViolado` / linha `rejected-scope`), (b) qualquer achado
  ficou `open`, (c) para o **aceite final** — `accepted` + refutação `upheld` só saem de
  `runFallback` completo. Re-verificação nunca publica scorecard 5/5.

**Funções a criar/mudar:**

| Onde | O quê |
| --- | --- |
| `scripts/lms-reverificar.mjs` (novo) | `reverificarPrompt(findings, diff)`, `parseReverificacao(stdout, stderr)`, `aplicarReverificacao(scorecard, results, verificados)` (pura), `runReverificacao({ root, env, collect })` |
| `scripts/lms-fix.mjs:registrar` | a linha de `.lms/fixes.jsonl` passa a carregar `marco` (o SHA/stash de `marcoDaArvore`) — hoje só grava `commit`, e sem o marco não há como recortar o diff do fix |
| `scripts/lms-fix.mjs:runFix` | ao fim, imprime o comando de re-verificação com os ids `fixed`/`claimed`; **não** dispara (ver §5) |
| `scripts/lms-reviewer-tmux.mjs:collectTmux` | aceitar `promptPath`/`outPath` por chamador em vez dos fixos `.lms/review-prompt.md` e `.lms/candidates/<provider>.json`, e aceitar `manterJanela: true` para não chamar `killWindow` no sucesso — sem isso não existe "mesma sessão com contexto preservado" (ver §6) |
| `package.json` | bin `lms-reverificar`, script `lms:reverificar` |

### 3.2 Classe repetida vira achado estrutural

Sinal: a mesma `lens` no mesmo `path` — ou no mesmo **prefixo de diretório** (primeiros
dois segmentos) — em **3 rodadas consecutivas**. As rodadas já são persistidas em
`.lms/history.jsonl` por `lms-reviewer-fallback.mjs:logAttempt`, mas hoje a linha não
carrega os achados; passa a carregar `{ lens, path, id }` de cada achado do scorecard.

Quando o gatilho dispara, o runner **emite um achado sintético** antes do estágio de
verificação:

```json
{ "id": "classe:<lens>:<prefixo>", "severity": "P1", "lens": "<lens>",
  "path": "<prefixo>/", "title": "classe recorrente: <lens> em <prefixo>",
  "found_by": "runner",
  "acceptance": "um teste que feche a CLASSE (propriedade, paridade ou tabela de
  cobertura) — corrigir só as ocorrências citadas não fecha este achado",
  "recurrence": { "rounds": ["…","…","…"], "ids": ["…"] } }
```

Consequências:

- **Fix pontual é recusado.** `lms-fix-routing.mjs:corrigivelPeloRevisor` devolve
  `{ ok: false, motivo: 'classe recorrente exige decisão de desenho' }` para todo
  achado com `recurrence`; em `runFix` ele cai em `escalados` (rota `orchestrator`).
- O achado sintético é `P1` e **bloqueia** como qualquer P1; sai da lista só quando
  uma rodada cheia deixar de reincidir a classe (não por re-verificação — §3.1 fecha
  achado de código, não achado de desenho).
- `findingId` (`lms-scorecard.mjs:178`) continua derivando id dos achados normais; o
  sintético usa id próprio, estável por construção, e o validador precisa aceitá-lo.

**Funções a criar/mudar:** `scripts/lms-classe-recorrente.mjs` (novo) —
`classeDe(finding)`, `classesReincidentes(historico, { janela: 3 })`,
`achadoEstrutural(classe, ocorrencias)`; `lms-reviewer-fallback.mjs:logAttempt`
(persistir achados na linha); `lms-reviewer-fallback.mjs:runFallback` (injetar o
sintético); `lms-fix-routing.mjs:corrigivelPeloRevisor` (recusa).

### 3.3 Golden set de evals do próprio LMS

Diretório `evals/` **no pacote**, versionado:

```
evals/
  casos/<slug>/patch.diff          # o diff revisado
  casos/<slug>/esperado.json       # { "p1": [{id, lens, path}], "fp_conhecidos": [...] }
  casos/README.md                  # proveniência e regra de anonimização
```

`esperado.json` distingue **achado real esperado** (tem de aparecer: conta recall) de
**falso-positivo conhecido** (se aparecer, conta FP). Casamento por `(lens, path)` +
`id` quando o id for estável; título nunca é chave.

Bin `lms-eval`: roda um provider/prompt contra o corpus e imprime
`{ casos, recall_p1, taxa_fp, por_caso }`, com exit 1 abaixo dos pisos
(`LMS_EVAL_RECALL_MIN`, default 0.8; `LMS_EVAL_FP_MAX`, default 0.2).

**Regra de processo:** trocar `reviewPrompt` ou acrescentar provider a
`LMS_REVIEWER_ORDER` exige rodada de `lms-eval` registrada no CHANGELOG. O provider
`pi` (v1.1.5) entrou sem essa medida — é o primeiro caso a rodar retroativamente.

**Fonte inicial:** `.lms/history.jsonl` e os relatórios Opus
(`REVIEW-FASE1/2/3-OPUS.md`) do consumidor, **anonimizados** — são artefatos de runtime
do repo do Master, gitignorados, e nada entra em `evals/` sem passar pela regra de
`casos/README.md`: sem nome de cliente, sem CNPJ, sem trecho de certificado, sem
`.env`. Curadoria manual, uma vez; não há importador automático.

**Funções a criar:** `scripts/lms-eval.mjs` — `carregarCasos(dir)`,
`compararAchados(esperado, obtidos)`, `runEval({ dir, env, collect })`.

### 3.4 Suíte verde como pré-condição de rodada

Degrau determinístico **antes** de gastar cota, imediatamente depois da triagem em
`scripts/lms-reviewer-trigger.sh` (que já trata `exit 10`):

- `lms.config.json` ganha a chave opcional `testCommand` (string ou `{ cmd, args }`).
  Sem a chave, o degrau é **pulado com aviso** — a config é opcional por desenho
  (`scripts/lms-config.mjs`, objeto `EMPTY`), e exigir teste de um repo que não tem
  suíte seria travar o gate para quem não pediu.
- Com a chave: o comando roda com timeout próprio (`LMS_TEST_TIMEOUT_MS`, default
  10 min) via `spawnEmGrupo`/`matarGrupo` (`scripts/lms-process-utils.mjs`), pelas
  mesmas razões do P1-4 da Fase 3.
- **Vermelho = rodada recusada**, exit dedicado (**11**, distinto do 10 da triagem),
  com as últimas 20 linhas da saída no stderr e **nenhum provider invocado**.
- Falha de ferramenta (comando inexistente, timeout) **não** é vermelho: avisa e
  segue — o precedente é a triagem, onde falha de ferramenta não dispensa revisão.
  Aqui a simetria é a mesma: erro de infra nunca decide sozinho.
- `LMS_TEST_GATE=0` desliga (mesmo padrão de `LMS_TRIAGE`/`LMS_VERIFY`).

**Funções a criar/mudar:** `scripts/lms-pre-rodada.mjs` (novo) —
`comandoDeTeste(config)`, `runPreRodada({ root, env })`;
`scripts/lms-config.mjs:loadConfig` (chave `testCommand`, validada por `str`);
`lms.config.example.json` (documentar); `scripts/lms-reviewer-trigger.sh` (bloco após
a triagem).

## 4. Testes exigidos

Sem rede, sem CLI real, `node --test` (`scripts/*.test.mjs`). O helper vem **antes** do
segundo teste irmão, nunca depois.

| Módulo | Casos mínimos |
| --- | --- |
| `lms-reverificar` | `closed` não altera `score`/`aggregate`; id ausente na resposta continua `open`; `closed` derrubado pelo verificador volta a `open`; `LMS_VERIFY=0` recusa a re-verificação inteira; aceite final nunca sai daqui |
| `lms-classe-recorrente` | 3 rodadas mesma `lens`+prefixo → sintético P1 com `acceptance` de classe; 2 rodadas → nada; rodadas não consecutivas → nada; sintético roteia para `orchestrator` em `corrigivelPeloRevisor` |
| `lms-eval` | recall e FP calculados sobre corpus fixture; caso com FP conhecido detectado reprova; exit 1 abaixo do piso; corpus vazio é erro, não 100% |
| `lms-pre-rodada` | sem `testCommand` → pula com aviso (exit 0); comando falho → exit 11 e nenhum collect; comando inexistente → aviso e segue; timeout mata o GRUPO (neto não sobrevive); `LMS_TEST_GATE=0` pula |
| `lms-scorecard` | achado sintético com `id`/`recurrence` passa `findingsShapeError` |

## 5. Fora de escopo (explícito)

- **Re-trigger automático após fix.** Decisão do Master de 2026-09-02, mantida: o
  disparo da re-verificação é **manual**. Um laço fix→revisão→fix sem humano no meio
  fecha achado com o incentivo de passar no gate. `runFix` imprime o comando; quem o
  roda é gente.
- **Validação do scorecard no CI remoto.** É a frente que encerra a classe "evasão
  local do gate" (registrada no `AGENTS.md` do consumidor) e não é resolvida por
  nenhum item desta fase. Frente separada.
- Fila própria para os `escalados` do modo `orchestrator` (dúvida 1 do relatório da
  Fase 3): continua sendo lista impressa.
- Qualquer afrouxamento do gate. Nenhum item desta fase pode reduzir o que já bloqueia
  — re-verificação só **fecha achado**, verificador só **rebaixa**, achado estrutural só
  **acrescenta**.

## 6. Riscos

1. **A sessão tmux não preserva contexto hoje.** `collectTmux` mata a janela do
   provider no sucesso (`killWindow` antes do `return { kind: 'ok' }`) e abre uma nova
   a cada coleta; a sessão (`sessionNameFor`) é reaproveitada, o **processo da TUI não
   é**. Sem a mudança da §3.1 a re-verificação nasce sem o contexto que a justifica —
   e vira só um prompt mais curto. Mitigação: `manterJanela` + prompt/candidato por
   caminho, com o *fallback* de janela nova e prompt auto-contido quando a janela
   morreu.
2. **Re-verificação como caminho de aceite barato.** Mitigado por construção: não sobe
   score, não emite `accepted`, e `LMS_VERIFY=0` a desliga.
3. **Achado estrutural falso.** Três rodadas de `lens`+prefixo podem ser três defeitos
   independentes no mesmo diretório. Mitigação: é P1 com `acceptance` de teste — o
   custo do falso positivo é escrever um teste de classe, que raramente é desperdício;
   e o achado é do `runner`, logo o contraditório existente pode derrubá-lo.
4. **Corpus de eval envelhece.** Um golden set que ninguém atualiza vira teto de
   qualidade. Mitigação: cada rodada que produzir um FP novo vencido por refutação já
   registra precedente (`lms-precedentes.mjs:registrarPrecedente`); a curadoria do
   `evals/` sai daí, não de coleta nova.
5. **Degrau de teste vira o gate.** Suíte lenta transforma todo push em espera.
   Mitigação: timeout próprio, `LMS_TEST_GATE=0` e a chave ser opcional.
